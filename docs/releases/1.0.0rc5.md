# autorun v1.0.0rc5

Date: 2026-11-20

1.0.0rc5 fixes defects found in 1.0.0rc4. The most serious: an
uninstall or upgrade could delete files you had added inside a skill or
extension folder that autorun installed, with no copy kept. The release also
fixes the Claude desktop app's task list, hooks run through the `autorun`
command in that app, stale Codex skill copies, task-tracking writes on a full
disk, and one hook failure under load on Linux. Three behaviors change: in the
Claude Code terminal and the Claude desktop app, `/ar:cache` now holds a prompt
sent after the prompt cache expired on a conversation of 100,000 tokens or more
(Changed item 1 has the conditions) instead of only warning; `/ar:ok` takes
several quoted patterns in one command; and Pi agents started by pi-subagents
0.68.0 or newer now get autorun's tool checks.

## Upgrading from 1.0.0rc4

Run one of these. Use the second if you installed the PDF backends
(`uv tool list --show-extras` lists `pdf`); the first removes them.

```bash
uv tool install --force 'autorun-ai==1.0.0rc5' && autorun --install
```

```bash
uv tool install --force 'autorun-ai[pdf]==1.0.0rc5' && autorun --install
```

After either command, check that `autorun --version` prints `autorun 1.0.0rc5`.
Keep the version pin (`==1.0.0rc5`): once a stable release exists, `uv` installs
that instead of this candidate. New installs use the same commands. The README
covers other harnesses and options: <https://github.com/ahundt/autorun#readme>.

Claude Code only: if you installed through its marketplace and not with `uv`,
run this instead of the commands above. The first half fetches the new release
into Claude's copy of the marketplace. That route does not run
`autorun --install`, so any setting this section says the install changes is
yours to add, and the steps below that run `autorun` need the `uv` install.

```bash
claude plugin marketplace update autorun && claude plugin update ar@autorun
```

1. If you keep your own files in a skill or extension folder that autorun
   installed, do not run 1.0.0rc4's `autorun --uninstall` before you upgrade:
   that version deletes them with the folder (Fixed item 6). The install
   commands replace 1.0.0rc4 in place.
2. Quit and relaunch each installed coding CLI or app and start a new session,
   because a session reads its hooks only when it starts. If you used the
   Claude Code marketplace route, also run
   `claude plugin install autorun-skills@autorun` first, because the
   marketplace update command updates `ar` only.
3. Nothing else is required unless you keep your own files in a folder autorun
   installed: Fixed item 6 lists the files a backup still does not cover, so
   copy those elsewhere before you upgrade.
   Config files, task state, and `/ar:` commands carry over. You will notice
   four things. The install may warn that it kept skill
   copies in `~/.agents/skills` that match no version it wrote, and it now
   replaces the ones it can prove are its own (Fixed item 3). A file you
   added to a folder autorun installed, under a name its ownership check skips
   such as `SKILL.md.bak`, is copied under `~/.autorun/installer/backups/`
   before that folder is removed or replaced (Fixed item 6). And autorun now keeps a
   file `~/.autorun/disk.reserve` of 8 MiB while the disk has room (Fixed
   item 4). To turn that off, put `{"disk_reserve_bytes": 0}` in
   `~/.autorun/autorun.config.json` and delete the file; the setting stops
   autorun creating it and does not remove one that exists. And in the Claude
   Code terminal and the Claude desktop app, a prompt sent after the prompt
   cache expired on a context of 100,000 tokens or more is held once, when
   the session's record states how long its cache lives or you set that with
   `/ar:cache set age`; send the same text again to proceed, or run `/ar:cache warn` to get the 1.0.0rc4
   notice back (Changed item 1).

## Changed

1. In 1.0.0rc4 `/ar:cache` warned that the prompt cache had expired and still
   sent the prompt; two Claude desktop prompts re-wrote 279k and 741k cached
   tokens that way. In the Claude Code terminal and the Claude desktop app,
   autorun now holds such a prompt when the conversation is 100,000 tokens or
   more and the cache lifetime is known, from the session's record or from
   `/ar:cache set age`. Send the
   same message again to send it once, or run `/ar:cache warn` to get the
   notice back in that session. Claude Code started another way (by T3 Code,
   for example) and the other coding CLIs warn by default; `/ar:cache on`
   makes such a session hold where its prompt hook can stop a prompt. On
   Claude Code, resending costs less than `/ar:cache ok`, because a slash
   command is itself a model request.
2. `/ar:ok` takes several literal patterns in one command when each is quoted:
   `/ar:ok 'git push' 'gh pr create' 'gh pr edit' 72h` allows all three for 72
   hours, where 1.0.0rc4 needed three commands and rejected the second quoted
   string. The count, duration or `perm` word applies to every pattern, and
   nothing is stored if one pattern is invalid. Every form 1.0.0rc4 accepted
   means what it did: an unquoted `/ar:ok git push` is still one pattern, and
   a word outside quotes that is not a scope word is still an error. A quoted
   word after the first pattern that is a bare count, duration or `perm`
   word, such as `'5m'`, is read as the scope, as before, so a pattern spelled
   that way goes first or in its own `/ar:ok` command. So does one that contains an escaped quote, and a
   `regex:` or `glob:` pattern can only come first. `/ar:no` is unchanged.

## Fixed

1. In the Claude desktop app's Code tab, autorun no longer pushes the session
   toward TaskCreate when the app has given it its own plan list,
   `mcp__ccd_turn__update_plan`. The app tells the model to use that list
   instead of the Task tools, and autorun's SessionStart message used to say
   the opposite. A desktop session now gets a conditional instruction: use the
   plan list if the session has it, otherwise load the Task tools as before.
   Once autorun sees the session call `mcp__ccd_turn__update_plan` (the call
   itself, not the tool merely being available), it names that list outright
   in its reply to that call, in a new session and in a resumed one. From then
   on, for that session, autorun no longer refuses to end a turn because Task
   tool tasks are unfinished, no longer reminds about tasks left untouched,
   and no longer lists earlier tasks when the session starts. A desktop
   session that never calls the plan list keeps the Task tools and those
   three checks, as do terminal and SDK sessions.
2. Hooks run as the console command `autorun --cli <harness>` now forward the
   same harness variables as `hooks/hook_entry.py`. The Claude desktop app
   loads the plugin's own `hooks/hooks.json`, which uses that command, and it
   forwarded none of them. So the daemon never saw
   `CLAUDE_CODE_ENABLE_TODO_TOOLS`, and every such session reported
   "autorun is not enforcing task tracking yet". Both paths now forward the same
   four variables: `platforms.forwarded_harness_env_names()` is the list, and a
   test fails if the copy in `hooks/hook_entry.py` differs.
3. Codex now gets this release's skills when an earlier autorun left copies
   in `~/.agents/skills` that lost their `.autorun-owned` marker, for example
   because that directory is kept in git and the marker was ignored. Those
   copies read as your own skills, so the install left them in place and
   Codex, which reads that directory, kept running them instead of its plugin's
   copies. An unmarked copy is now autorun's when every file in it is
   byte-identical to a version autorun installed: the install records what it
   publishes in `~/.autorun/installer/published-trees.json`, a file outside
   the skill folders that survives a lost marker, and it carries a list of the
   skill versions autorun committed before that. Such copies are retired and
   the packaged ones take over. The comparison is by content, so a copy of a
   shipped version that you placed there by hand, unchanged, counts as
   autorun's too. A copy you edited, or a skill you wrote, is kept as before, and the warning now says it matches no version autorun
   wrote. A folder that also holds a file of yours is kept too, even when the
   file has a name the comparison skips elsewhere, such as `SKILL.md.bak`,
   `notes~` or `.git/`. Only operating system and Python leftovers
   (`.DS_Store`, `*.pyc` and similar) are ignored in this comparison; the
   backup in item 6 skips a longer list. The record of what the install
   published is taken from the copy autorun staged, before it becomes visible,
   so an edit you save right after an install cannot be mistaken for autorun's
   own text. One case is not handled: an old skill folder whose name differs
   from the shipped one only by letter case (`Commit` against `commit`) is not
   recognized as the earlier copy. On a case-sensitive filesystem it is left
   beside the new folder. Nothing is deleted.
4. When a full disk stops autorun from opening or saving its own state or
   starting its daemon, autorun now frees a file it holds for that purpose and
   tries once more; the limits are listed at the end of this item. On
   2026-11-13 SQLite could not create its `-wal` and `-shm` files
   (`unable to open database file`) and every tool call was refused, so the
   agent that had to free space could not run a command; on 2026-11-15 a full
   disk also stopped the daemon from starting, because creating `daemon.flock`
   failed with ENOSPC. autorun now keeps `~/.autorun/disk.reserve`, 8 MiB
   (`disk_reserve_bytes`; 0 stops autorun creating it), created while the volume has four
   times that free. When opening the SQLite state database, saving the JSON
   state file, taking the daemon lock or creating the daemon's socket fails on
   a volume with under half the reserve free, autorun deletes the reserve and
   retries once; the daemon recreates it when space returns. A real
   full volume that made the 1.0.0rc4 daemon degrade every tool call
   (`state_evaluation_failed`) now runs them normally. Guarded deletions still
   need `/ar:ok rm` typed by you, which works again once state can be written.
   The reserve has limits. It does not cover a write that fails inside an open
   SQLite transaction. It
   frees bytes, not inodes, so a volume that has run out of inodes is not
   helped. On a volume with snapshots or transparent compression, deleting it
   may free less than 8 MiB. For the JSON save, the daemon lock and the
   daemon's socket, only an out-of-space error on the reserve's own volume
   releases it; a permission error on a nearly full disk leaves it in place.
   A state file reached through a symlink onto another volume is not covered. Creating or releasing the reserve cannot itself
   raise an error: a failure there is logged and ignored. When the daemon
   lock cannot be created, the log warning now names the lock path and the
   error number (for example `errno 28, No space left on device`). It used to
   print `(NFS?)` and the error text with no path.
5. A hook sent while the daemon's connection queue is full is now retried
   instead of failing with "Daemon accepted the request but did not answer:
   ConnectionResetError('Connection lost')". On Linux such a connection attempt
   returns a socket that never connected, and the request written to it went
   nowhere. 1.0.0rc4 retried this when the first read failed (EINVAL) but not
   when the first write did. `ipc.connect` now asks the socket for its peer
   and reports a socket without one as a refused connection, before anything
   is sent, so the client waits and reconnects.
6. Uninstalling or upgrading autorun deleted a skill or extension folder it
   had installed together with files you had added to it, with no copy. This
   covered names such as `SKILL.md.bak`, `notes~`, `.git/` and `__pycache__/`,
   which the install's ownership check skipped, and it happened on uninstall, on
   upgrade, when the install adopted a folder, with `--force`, and when the
   install replaced a folder it had proven to be its own with a link. Before
   it removes or replaces a folder, autorun now looks through it once. If it
   finds a file that is not one autorun installed, it copies the folder to
   `~/.autorun/installer/backups/` first. It
   ignores files an operating system or Python regenerates (`.DS_Store`,
   `._*`, `Thumbs.db`, `*.pyc`), test and lint caches (`.pytest_cache`,
   `.mypy_cache`, `.ruff_cache`, `htmlcov`, coverage files), and the `.venv` of
   an old Claude plugin cache version, so an ordinary upgrade makes no backup.
   Four limits remain. In a folder that has no autorun marker and is known to be
   autorun's only from a harness's install record, a file of yours under an
   ordinary name such as `notes.md` is still not covered. A file of yours that
   carries the name of a harness's own record (`qwen-extension.json`,
   `.gemini-extension-install.json`), or sits in a `.venv` folder below the top of a
   Claude plugin cache version, is treated as that record or runtime: it does
   not cause a backup, and the `.venv` content is left out of one made for
   another file. A named pipe (FIFO) inside a skill or extension folder,
   under a name the install reads, makes the install wait forever on it; stop
   that install, remove the pipe and run it again.
   And apart from a forced refresh of a Claude plugin cache, the install
   output does not name the backup it made, so look in that directory after
   an upgrade or uninstall if you kept files in an autorun folder.
7. Starting a session cost more CPU the more sessions the daemon had cached. Each
   state write scanned every cached key of every session, and each
   `get_session_manager()` call resolved the state directory path again, about
   seven times per hook. A write now looks up only its own session's keys, and
   the resolved path is remembered per unresolved input. On macOS 300 session
   starts drop from about 0.31 s to about 0.28 s of CPU, and the cost no longer
   grows with the number of cached sessions. A state directory symlink that is
   retargeted while the daemon runs is not noticed until it restarts.
8. Pi agents started by the pi-subagents add-on ran tools without autorun's
   checks unless each role was set up to load autorun. With pi-subagents
   0.68.0 or newer, autorun now registers itself with the add-on so the agents
   it starts load autorun without that setup, and Pi without the add-on works
   as before. autorun still cannot tell a foreground child agent
   apart from its parent session.
9. `autorun --status` now uses the `--skill-placement` value you give it. It
   accepted the option and ignored it, so after `autorun --install
   --skill-placement both` a status check listed every shared skill copy as
   `retire ... no longer shipped` and exited 1. The option still applies only
   to the command it is given to: a later `autorun --install` without it
   returns to the placement set in the environment or the config file, or to
   the default, and under the default it removes those shared copies.

## For contributors

1. A tmux test failed once per run on GitHub's `ubuntu-latest` after it moved to
   Ubuntu 26.04 (tmux 3.6a): the suite's private tmux server exited when a test
   closed its last session, and the next test's first command raced that exit.
   `tests/conftest.py` now writes a `tmux.conf` with `exit-empty off`, and the
   server runs for the whole pytest session.
   `test_the_private_tmux_server_outlives_its_last_session` covers it.
2. `test_session_targeting_regression.py` sent Ctrl-C to a shell that had not
   yet installed its signal handlers on the same runners, which closed the
   session. `setup_method` now checks that `new-session` succeeded and waits
   for a shell prompt, and a failed send reports the server's sessions and
   panes.
3. `test_revision_3_upgrade_cost` in `test_state_store_benchmark.py` timed one
   migration per size and failed when a shared runner stalled once. It now
   builds three fresh stores per size and keeps the fastest.
4. `test_300_session_starts_need_less_cpu_than_the_start_deadline` stopped
   measuring at `<=` while asserting `<`, so a pass exactly at the 2 s deadline
   failed with `assert 2.0 < 2.0` and no detail. The early exit now uses `<`,
   and the failure message lists every pass to four decimals.
5. `test_host_task_list.py` pins that a Codex, Gemini, Qwen, Pi, or any other
   non-Claude harness started inside a Claude desktop session ignores the
   inherited `CLAUDE_CODE_ENTRYPOINT` and `CLAUDE_CODE_TERMINAL_MCP_TOOLS`
   variables. `test_install_provenance.py` and `test_install_fs.py` pin the
   no-loss and no-backup-for-junk rules of Fixed items 3 and 6.
6. `scripts/release_notes.py` now puts the two `uv tool install` commands first
   in the generated Upgrading section and the Claude Code marketplace route
   second, labelled "Claude Code only".
